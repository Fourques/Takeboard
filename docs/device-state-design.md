# SSH 已经连上，为什么生成服务还没就绪？

TakeBoard 开发笔记 · 2026-09-28

把远端 GPU 接进桌面创作工具，很容易写出一个看似方便、实际误导人的判断：HTTP 端口不通，所以设备离线。

但用户配置的是一台机器，不是一个永远存在的端口。机器能通过 SSH 访问，ComfyUI 可以还没启动；GPU 可能正忙；服务进程可能存在，但 API 仍未就绪。把它们都塞进一个红色“未连接”，会让用户重复添加设备、反复启动服务，最后不知道自己到底连到了哪里。

## 用不同事实回答不同问题

| 层级 | 回答的问题 | 不应该推出的结论 |
| --- | --- | --- |
| 已保存设备 | 用户配置的是谁 | 当前一定在线 |
| SSH 连接 | 能否访问远端机器 | ComfyUI 一定启动了 |
| GPU 观测 | 当前能看到哪些资源 | 任意模型都装得下 |
| 服务进程 | 服务是否停止、启动中或运行 | HTTP API 已可用 |
| 生成 API | 是否能与 ComfyUI 通信 | 任意工作流都能执行 |
| 工作流与任务 | 输入、依赖和资源是否满足本次请求 | 后续任务一定成功 |

TakeBoard 的 beta.17 把设备连接、GPU、服务和启动决策拆开。SSH 连接成立之后独立读取机器信息与 GPU 数据。GPU 读取失败只影响资源信息，不改写成“设备断开”。服务未启动也是正常状态，而不是要求用户重新添加设备的错误。

## 同一个错误，只让一层负责展示

资源探测失败如果在设备卡、服务卡和按钮下各显示一次，用户会误以为出了三件事。统一状态来源后，主视图给出设备、资源、服务三个结论；底层诊断进入次级详情。启动和重连也根据服务状态选择，不把两个不同操作都叫“连接”。

另一个不明显的问题是异步结果：用户删除设备时，旧探测可能还在运行。必须在写回前检查设备是否还存在、目标配置是否已改变，避免删除后“又出现”。探测合并与短期缓存可以减少重复 SSH 查询，但缓存不是身份。

## 真实测试不能被安全阈值替代

一次实测中，4090 只剩约 265 MiB 显存。即使没有提交生成、没有加载生成模型，空 ComfyUI 仍在 CUDA 初始化时发生内存不足。测试服务随后停止，没有终止其他 GPU 任务。

这只能证明那次环境不足以启动，不能推导出所有 ComfyUI 都必须预留 4 GiB。beta.17 的远程启动仍是保守策略：已配置的 Linux 用户级 systemd 服务、可确认的单 NVIDIA GPU、资源检查通过。它不是跨平台自动安装器，也不是精确模型内存预测器。

## 对创作者的意义

最终界面应能自然表达：“设备已连接，生成服务未运行”。用户可以先查看机器，也可以稍后再启动生成。端口重现只更新服务状态，不代表新设备；未知状态不能被包装成成功。

这还不是通用远程调度的终点。不同 SSH 别名、外部手动隧道和多 GPU 归属不能靠猜测合并；安装包能启动，也不意味着所有模型经过验证。
